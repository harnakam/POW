# Codexタスクの最適化手順

## 1. 先に「どこまでの時間か」を決める

| 指標 | 開始と終了 | 主な用途 |
| --- | --- | --- |
| コマンド内部時間 | コマンド内の開始から終了 | アルゴリズムやテスト実行の改善 |
| ツール待ち | ツール呼び出しから結果受信 | 起動、フック、実行、転送を含む待ちの観測 |
| 固定ワークフロー | 最初のツール開始から最後の結果受信 | 呼び出し間のモデル往復を含む比較 |
| 実装・検証完了 | 依頼処理開始から必要な検証の成功 | 成果物を確認できるまでの時間 |
| タスク全体 | 依頼処理開始から最終回答後の完了イベント | ユーザーが一連の作業を待つ時間 |

この表の境界を混ぜない。0.8秒の検証バッチが、0.8秒でアプリを作れたことを意味するわけではない。最終回答前の数字は途中時点であり、完了イベント取得後の値と区別する。UI表示の描画時間は、クライアントのログ境界とも異なる。

必要な計測器が既にあるなら、ラベルと出力先を指定して使う。計測器の作成、計測器自身の待機、集計、説明にも時間がかかる。重い監視や全ログ収集を、簡単なタスクの既定動作にしない。

## 2. Thinkingを一括して原因扱いしない

利用可能なイベントを使い、次の区間を分ける。

- モデル要求から最初の出力項目まで。
- ツール引数の生成・受信区間。
- reasoning項目のストリーム区間。
- ツール呼び出しから結果受信まで。
- 説明・最終回答の出力区間。
- 上記では説明できない処理・イベント境界。

ストリームの開始・終了イベントは純粋な計算時間ではない。要求から初回項目までにもネットワーク、サービス側の待機、入力処理などが混ざる。ツール待ちにはシェル・インタープリター起動、フック、実コマンド、結果転送が含まれうる。観測できない内訳は不明と記載する。

重複区間には分類の優先順位を決め、合計が経過時間と一致するか確認する。並列コマンドの実行秒や子エージェントの秒数を単純に足して、全体時間にしない。親だけのログを集計した場合は、その範囲を明記する。

## 3. 新しいコードより既存の入口を先に探す

次の順で、必要な最小限だけ調べる。

1. リポジトリの指示とpackage scripts、既存タスクランナー。
2. 既存スクリプト、短いプリセット、過去の計測成果物。
3. 索引がある場合はシンボル検索。内容変更で無効化される索引を使う。
4. 足りない機能だけ既存の入口を拡張する。

長いインラインコードを毎回モデルに生成させると、引数生成、引用符の誤り、レビュー、再実行の費用が増える。繰り返す実処理は保存済みスクリプトや既存タスクへ寄せる。aliasの追加だけでコマンド本体の実行が速くなるわけではないが、繰り返し生成する文字数は減らせる。

`cxd check`等は調査時に使ったローカルディスパッチャの例であり、このPOW Skillには同梱していない。存在する環境だけで使用し、未導入の環境では実在するpackage scriptやランナーを使う。短い名前だけを作り、存在しない実装やキャッシュ済み成功を返してはいけない。

「新規作成」を頼まれた場合、旧成果物を実行しただけ、別ファイルにコピーしただけなら新規実装と説明しない。ゲーム本体の再利用と、テスト・計測基盤の再利用は別に記録する。新しいファイル名だけでは、設計まで独立した実装の証明にならない。

## 4. コマンドを非同期にする

独立した読み取りや検証は、既存の実行器でまとめ、上限付きで並列実行する。ジョブID、依存関係、終了コード、タイムアウト、完了通知、元ログを維持する。競合する書き込みは直列化する。

Codexの`functions.exec`が使える場合、独立したツール呼び出しを`Promise.allSettled`等で待ち合わせ、すべての結果を確認できる。長いバッチは、利用可能なら`yield_control`と`notify`を使い、待機をランタイム内に残す。待機中も親は独立した仕事を進める。

返ったsession IDの監視コードを毎回生成しない。既存ブリッジを再利用する。`functions.exec`の終了時に未awaitのPromiseが破棄される環境では、投げっぱなしにして完了したことにしない。実行中のPromiseを生かす方式で待機・完了通知を管理する。

非同期化と次の改善は別物なので、報告でも分ける。

- 常駐ワーカー: プロセスや読み取りキャッシュの再利用。
- 短いコマンド: 引数生成量の削減。
- 一括呼び出し: モデルへの往復回数の削減。
- 並列実行: 独立した処理の重なり。

常駐ワーカーは通常の権限境界を維持する。読み取り専用操作を限定し、任意コード実行の入口にしない。テストやコマンドの分離を維持し、不要になったワーカーを停止する。短命なツール呼び出しの子プロセスが終了時に停止する環境では、常駐が呼び出し間で維持されているかPID等で確認する。

## 5. マルチエージェントは必要なときだけ使う

| 作業 | 推奨 |
| --- | --- |
| 小さなCLI、短い修正、密接に依存する変更 | 親で実行 |
| 決まったコマンドの実行・待機 | コマンド実行器 |
| 独立した調査、合意済みインターフェースで分離できる実装、独立レビュー | 最小限の子エージェント |

委譲前に目的、入出力、変更可能ファイル、前提、完了条件を揃える。同じファイルを複数の実装者に渡さない。子が作業している間、親はテスト準備や別の統合作業を進める。開始直後に全員の完了を待つだけなら、並列化の効果は薄い。

このPOWコレクションの`multi-codex`はユーザー可視のMainタスクを作る別用途であり、内部の小さな委譲を同コマンドに置き換えない。利用できる子エージェント機能がなければ、代替の独立タスク作成を無断で行わない。

非同期ツールは、単一の親モデル要求の生成速度を上げない。複数のモデル要求を並行に走らせる構成には、起動、文脈転送、統合、再検証の費用がある。子の出力も全量読み込まず、担当範囲と判断に必要な証拠を受け取る。

## 6. 出力圧縮とキャッシュを適切な場所に使う

RTK等の既存出力圧縮は、ノイズの多い出力に使える。圧縮しても終了コードと失敗診断を維持し、回復IDが返る場合は元ログを取得して原因を確認する。厳密なJSON、ソース、時刻、算術の検証には必要な原文を保持する。出力圧縮と、入力引数の短縮は別の効果として測る。

ソースのAST・シンボル情報は内容ハッシュで無効化し、変更・削除・構文エラーを反映する。成功したテスト結果はキャッシュしない。新しい圧縮製品、常駐サービス、APIプロキシを自動導入しない。

## 7. 一つ変えて同じ仕事を比較する

1. 同じ入力・ソース・検証内容と出力の意味を固定する。
2. キャッシュの冷温、並列上限、起動を含むかを記録する。
3. 問いたい仮説を一つ決める。例: 独立した3回の呼び出しを1回にすると、往復を含む所要時間が減るか。
4. 負荷の変動に偏らないよう、可能なら順番を入れ替えて比較する。
5. 中央値だけでなく各サンプル、件数、失敗、元ログへの参照を残す。
6. 差がばらつきに埋もれる場合は結論を保留し、不要な複雑さを残さない。

最適化前後でテストを削ったり、サブプロセス検証をすべて置き換えたりして、同じ検証が速くなったことにしない。検証範囲を変える場合は変更を明示する。文字数削減からトークン数や失敗率の削減率を算出しない。

モデル品質、プラグイン、セキュリティ設定を速度のために変えない。環境制限でローカルソケットが止まる場合、アプリの不具合と区別し、許可された通常環境で検証する。ファイアウォールを無効化したり、グローバル設定を書き換えたりしない。

## 8. 終了時に残す情報

変更した入口、実行した検証、測定境界、開始・完了時刻、経過時間、サンプル数、比較可能性、キャッシュ状態、残る不明区間を短く報告する。公開用の資料には集約した数値だけを載せ、ユーザー名、端末パス、スレッドID、会話本文、認証情報を持ち出さない。

「タスク全体を10倍」「無駄時間ゼロ」は実測なしに約束しない。[実測記録](measurements-2026-10-19.md)の小さな比較も、一般化できる保証値ではない。
