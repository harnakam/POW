# /update: evolving workflow evidence

Researched and implemented 2026-10-30. Scope: a standalone installed Skill that discovers local workflows, retains bounded observations, invalidates stale plans and executes explicitly approved local steps. It does not train a model, infer authorization from history or automatically publish anything.

## Sources and decisions

| Source | Evidence and adoption decision | Limits |
| --- | --- | --- |
| [Node 20.19.0 child_process](https://nodejs.org/download/release/v20.19.0/docs/api/child_process.html) | Use spawn with explicit argv, shell:false, windowsHide, finite timeout and bounded output. Windows batch wrappers need a shell, so restrict execution to the current Node executable plus reviewed relative script arguments. | A process can spawn children and perform effects before termination; this is not an OS sandbox. Windows tree termination is best effort. |
| [npm v10 scripts](https://docs.npmjs.com/cli/v10/using-npm/scripts/) | npm scripts have lifecycle, shell and environment semantics. Keep shell declarations and any workflow with pre/post hooks manual rather than silently changing their meaning. | Direct Node execution does not reproduce npm PATH or npm_* variables; the reference states this. No npm.cmd workaround or dependency install. |
| [Git log documentation](https://git-scm.com/docs/git-log) | Fixed read-only log arguments inspect at most 50 commits' changed names; file touch counts supply repository-specific recurrence evidence. | Touches do not establish command execution or successful outcomes. No commit messages, patches or credential-bearing remotes are retained. |
| [GitHub Copilot Memory](https://docs.github.com/en/copilot/concepts/prompting-and-context/copilot-memory) | Separate accumulated detail from authoritative instructions; reject secret-bearing memory and review applicability. Adopt provenance, bounded state and current-input checks. | Documentation describes another product, not a guarantee that this implementation detects every secret or stale dependency. |
| [OpenAI Agents SDK memory](https://openai.github.io/openai-agents-python/sandbox/memory/) | Memory may be stale; prefer the current environment. Adopt re-reading live inputs before planning and executing rather than replaying stored commands. | No SDK or remote memory service is needed or imported. |
| [GitHub Community discussion 197646](https://github.com/orgs/community/discussions/197646) | A user reports unsolicited actions despite explicit constraints. Adopt an explicit reviewed plan and consumed per-attempt token; discovery and positive outcomes never grant permission. | Anecdotal user complaint, not a controlled evaluation or a claim that all agents fail this way. |
| [Reddit: stale context in agent memory](https://www.reddit.com/r/aiagents/comments/1wotyiq/how_are_you_handling_stale_context_in_agent_memory/) | User reports formerly correct project assumptions resurfacing after decisions changed. Adopt source hashes, scan expiry, replacement of current candidate definitions and historical outcome separation. | Comments are qualitative reports, not measured reliability or speed improvements. |
| [Reddit: persistent memory for coding agents](https://www.reddit.com/r/LocalLLaMA/comments/1r5q7xd/how_are_you_handling_persistent_memory_for_ai/) | User describes compaction losses and the possibility of persisting malicious retrieved instructions. Adopt local structured metadata, no conversation scraping, no source-text instruction promotion and no raw output storage. | No automatic semantic extraction or comprehensive prompt-injection detector is claimed. |

The two Reddit reports and GitHub complaint are used as problem evidence only. Their suggestions are not trusted commands. No upstream implementation or forum text was copied into executable code. The implementation is original Node standard-library code under the repository's POW Source-Available License 1.0; the consulted websites retain their own terms. No new production dependencies, downloaded source, background services, databases, MCP servers or telemetry were introduced.

## Local evidence and behavior

Inspected `package.json`, `.github/workflows/ci.yml`, recent commit subjects and existing POW entry points before implementation. This repository declares `validate` as `node scripts/pow.mjs validate`, and CI references `npm run validate`. A read-only scan at HEAD `b38b881e137995e45aebffb54194590ad5f96f0b` reported four relevant entry-point touches in the last 50 commits and a runnable validate candidate. The `node --test` declaration remained manual; it was not executed. Commit subjects were inspected by the engineer but are not read or retained by the CLI.

State schema v1 lives at target `.pow/update/state.json`. It stores canonical-root identity hash, revision, input hashes, HEAD, evidence and at most 50 actual outcome records. A written scan evolves current candidates, prunes outcomes older than 90 days and preserves recent failures. A plan uses live argv reconstructed from current package data, not argv supplied by memory. Source/HEAD/runtime/platform changes or seven days since scan invalidate execution. Tokens include workflow, input fingerprint, root, revision and timeout; each attempted run consumes its token before launch, leaving an interrupted record if the parent crashes.

The executable subset is intentionally conservative: reviewed simple Node file argv only, with no shell, loader flags, inline execution, npm hooks or known publish/deploy/destructive names. Arbitrary source behavior cannot be classified by its name. The Skill therefore requires agent review of the entry point/imports and task authorization; discovered external effects remain separately authorized manual actions. Broad semantic workflow discovery and generic CI replay were rejected because they would confuse declarations with authority and expand the execution surface.

## Direct execution evidence

No tests, fixture files, benchmark suite or new verification harness were added. No `npm test` was invoked. Ran:

1. `node --check commands/update/scripts/update.mjs` — exit 0.
2. `node commands/update/scripts/update.mjs scan --root C:\Project\Agent\POW-delivery` — exit 0, complete read-only scan, CI/history evidence above. No `.pow` state created by that invocation.
3. A direct PowerShell-driven scenario initially used the execution tool's isolated TEMP directory. State persistence failed there and no execution approval was produced. The CLI returned nonzero; this was not counted as success. Recreated the same ephemeral workspace at `C:\Project\Agent\update-scenario-local`, outside shipping files, where state was writable.
4. In that isolated workspace, `scan --write`, `plan`, then `run --workflow package:verify --approve <current-token>` executed `node verify.mjs` containing `process.exit(7)`. CLI exit 1, persisted status `exit-failure`, child exit 7.
5. Repeating `run` with the consumed token was refused with exit 1. Editing verify.mjs to print a success message made the next read-only plan stale. A new written scan and plan produced a new token; the approved run exited 0 with `success`. State retained both outcomes. `package:publish` and a workflow with a `prehooked` lifecycle script stayed manual. The `.env` sentinel and raw stdout text were absent from persisted JSON.

Stopped runtime verification after that successful scenario. Windows was exercised; macOS/Linux execution, timeout/tree termination, output-limit enforcement and bound-exceeded paths were reviewed in code but not separately exercised. Parent integration owns full Skill validation and standalone installer verification after all sibling changes are ready.

To reproduce independently, create a new directory outside shipping files, write `package.json` with `{"scripts":{"verify":"node verify.mjs"}}` and verify.mjs with `process.exit(7)`, then perform step 4 with its own root. Change the script, observe stale plan, rescan, inspect the new plan and approve its new token. Do not reuse tokens from this note. Runtime outcomes remain metadata; raw output is deliberately discarded to avoid capturing secrets.

Remaining risks: excluded dependency/build/secret inputs are outside fingerprint coverage; package workflows needing npm's environment require manual execution; review tokens are not authentication; changes racing the launch are outside the preflight check; arbitrary approved source can perform effects; process-tree containment is best effort. No claims of measured speed, token savings or autonomous semantic learning are made.
